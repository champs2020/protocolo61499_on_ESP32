## Complete description of the fix

The build initially appeared to fail because the active ESP-IDF Python environment lacked `click`. That was an **environment activation issue**, not the firmware’s code error. I used the installed ESP-IDF 5.5.4 Python environment and ran the build to expose the actual errors.

### Root cause and fixes

1. **Open62541 was selecting the wrong architecture.**  
   The vendored Open62541 header had `UA_MULTITHREADING 0`, but its FreeRTOS/LwIP architecture wasn’t selected. It defaulted to POSIX, while parts of the amalgamated source expected FreeRTOS, resulting in missing lock macros and `timerMutex`/`serviceMutex` errors.

   I configured the component to select FreeRTOS/LwIP, explicitly require ESP-IDF’s `freertos` and `lwip` components, and link Open62541 as a whole archive. The whole-archive setting is needed because FORTE is itself linked from a static archive. I also removed the separate Open62541 dependency from `forte_main` to avoid pulling the whole-archived library in twice.

   The project now registers the Open62541 component through `TestApplication/CMakeLists.txt`. Its configuration is in `open62541lib/CMakeLists.txt`.

2. **The FreeRTOS clock source used an obsolete include path.**  
   ESP-IDF 5.5 provides the header as `freertos/task.h`, not `task.h`, so I updated the include in `open62541.c`.

3. **A compiler warning stopped the build.**  
   GCC reported that the result in Open62541’s secure GUID function might be uninitialized. I zero-initialized the local value before filling it with random bytes. This does not change the successful random-generation path.

4. **Open62541 API and symbol compatibility needed updates in FORTE.**
   - The local server now calls `UA_gethostname`, using the LwIP-compatible hostname function instead of POSIX `gethostname`.
   - The hostname declaration in `open62541.h` now has C linkage. Without that, C++ FORTE code requested a mangled C++ symbol while Open62541 provided a C symbol.
   - The server hostname configuration now copies into `customHostname` and reports a copy failure, instead of calling an unavailable API: `local handler`.
   - Cleanup now uses `forteUaDelete`, which calls `UA_clear` and `UA_free`, at the affected call sites in `opcua_helper.cpp` and `opcua_local_handler.cpp`.
   - Client code was updated for the Open62541 API used by this build: it checks session state with `UA_Client_getState`, uses `UA_Client_connectUsername`, and adopts the newer callback signature in `opcua_client_information.cpp` and `opcua_client_information.h`.

   Subscriptions and subscription events remain enabled; disabling them was an earlier workaround attempt, not the final fix.

5. **The app needed the rebuilt FORTE archive.**  
   I rebuilt `forte-static`, copied it to the ESP app, and verified the source and app copies had identical SHA-256 hashes. The resulting archive is `libforte-static.a`.

### Verification

The full ESP-IDF build completed successfully and generated `TestApplication.elf` and `TestApplication.bin`. The image fits the app partition, with 52% free. This verifies compilation, linking, and image generation; I did not flash or test the firmware on the hardware.

## Correction procedure: `ESP32_LOGGER` returns `UNSUPPORTED_TYPE`

### Symptom

The management request to create an FB with `Type="ESP32_LOGGER"` returned `UNSUPPORTED_TYPE`, even though the custom FB source files were present.

### Root cause

The implementation was not being compiled into FORTE and registered at startup. The module CMake file used `forte_add_directory_module()`, which treated it as the optional `EXTERNAL_ESP_LOGGER` module; that option was OFF. The request's type name was correct. The fix was to declare `ESP_LOGGER` as an enabled FORTE module and rebuild the static library consumed by the ESP-IDF application.

### Steps performed

1. **Enable the custom module.** In `forte_2/src/modules/ESP_LOGGER/CMakeLists.txt`, replace the directory-module setup with:

   ```cmake
   forte_add_module(ESP_LOGGER ON "ESP32 GPIO logger function block")
   forte_add_all_sourcefiles()
   ```

   The FB implementation registers the type `ESP32_LOGGER` with `DEFINE_FIRMWARE_FB`. Keep the XML request's `Type` value exactly `ESP32_LOGGER`.

2. **Reconfigure and rebuild FORTE.** Use the FORTE source and build directories already used for this application, explicitly enabling the option:

   ```powershell
   cmake -S C:\esp\projects\forte_2 -B C:\esp\projects\forte_2\build -DFORTE_MODULE_ESP_LOGGER=ON
   cmake --build C:\esp\projects\forte_2\build --target forte-static -- -j4
   ```

   The rebuilt library is `C:\esp\projects\forte_2\build\src\libforte-static.a`.

3. **Copy the rebuilt library into the ESP-IDF application.**

   ```powershell
   Copy-Item C:\esp\projects\forte_2\build\src\libforte-static.a C:\esp\projects\esp-4diac-forte\test_apps\TestApplication\components\forte_main\libforte-static.a -Force
   Get-FileHash C:\esp\projects\forte_2\build\src\libforte-static.a -Algorithm SHA256
   Get-FileHash C:\esp\projects\esp-4diac-forte\test_apps\TestApplication\components\forte_main\libforte-static.a -Algorithm SHA256
   ```

   Confirm that the two hashes match. Replacing the archive in the app is necessary; rebuilding FORTE alone does not update the library already consumed by ESP-IDF.

4. **Build the ESP-IDF application.** From an ESP-IDF 5.5.4 environment, build `C:\esp\projects\esp-4diac-forte\test_apps\TestApplication`. If `idf.py` reports `No module named 'click'`, activate the installed ESP-IDF Python environment (`idf5.5_py3.13_env`) before building; that message indicates the wrong Python environment, not a FORTE module error.

   ```powershell
   idf.py -C C:\esp\projects\esp-4diac-forte\test_apps\TestApplication build
   ```

   The build produces `build\TestApplication.bin`. Flash that image to the target board and restart it before testing. For example, replace `COMx` with the board's serial port:

   ```powershell
   idf.py -C C:\esp\projects\esp-4diac-forte\test_apps\TestApplication -p COMx flash monitor
   ```

5. **Verify the management request on the running device.**

   ```xml
   <Request Action="CREATE" ID="7">
     <FB Name="ESP32_LOGGER_BLINKY" Type="ESP32_LOGGER"/>
   </Request>
   ```

   A successful correction means the request is no longer rejected with `UNSUPPORTED_TYPE`. If it still is, first confirm the board was flashed with this newly built image and restarted. Then check that the FORTE build has `FORTE_MODULE_ESP_LOGGER:BOOL=ON`, that generated `forteinit.cpp` includes the logger FB and calls `FORTE_ESP32_LOGGER::dummyInit()`, and that the copied archive is the rebuilt one.

### Verification status

The module option was ON, the generated FORTE initialization included the logger FB, and the ESP-IDF build completed with the rebuilt archive. This confirms compile-time inclusion and firmware linking. The firmware still needs to be flashed and the management CREATE request needs to be tested on hardware; do not treat the runtime response as verified until that test succeeds.

The FORTE OPC UA loop calls `UA_Server_run_iterate(server, false)`, which polls the network non-blockingly and then waits on a semaphore. ## Branch status: 4diac OPC UA server control and ESP32 heap limitations

This branch adds a 4diac SIFB named `ESP32_OPCUA_SERVER_1`. It has `INIT`, `START`, `QI`,
`INITO`, `CNF`, `QO`, and `STATUS`. The `START` event calls `opcua_server_start()` through
the real C-compatible `opcua_server.h` API. Server startup is no longer automatic in
`main.c`; it is activated by the 4diac application.

The FORTE and ESP-IDF static libraries were rebuilt and linked. The ESP32 firmware with
the SIFB builds and has been flashed successfully. The server can receive HEL and OPN
messages, open a SecureChannel, create an UaExpert session, create a subscription, and
create and publish a monitored temperature item.

### Heap and memory problem

The ESP32 is a single-memory-domain system from the application's point of view: FORTE,
Wi-Fi, the DHT22 task data, open62541, network buffers, sessions, subscriptions, monitoring
messages, and 4diac management communication share the same internal RAM. It does not
automatically reserve enough additional memory for simultaneous clients and monitoring.

Observed in this project:

* Startup could leave little heap for Namespace 0 and fail with `BadOutOfMemory`.
* Reducing the open62541 send/receive buffers from 16 KiB to 8 KiB allowed HEL/OPN
  processing to proceed.
* Limiting the server to one SecureChannel, one Session, and one Subscription reduced
  allocations.
* Replacing the OPC UA task stack with a staged 6144-byte stack was tested as a memory
  reduction, with a stack high-water diagnostic. Network buffers must not be reduced below
  8 KiB because open62541 validates SecureChannel send/receive buffers.
* UaExpert and the standalone OPC UA server worked together while 4diac Watch was stopped.
* Adding 4diac Watch during active OPC UA sessions reduced the free heap and largest
  contiguous block, closed the 4diac management connection, and could trigger heap,
  message-processing, or task-watchdog failures.
* Disconnecting UaExpert deleted its session, subscription, and monitored item and
  recovered part of the heap.

The heap problem is primarily fragmentation and concurrency, not just the temperature
application. A low free heap sample is more useful with the largest contiguous block.
For example, `free=5980 largest=3968` leaves less than 4 KiB for one contiguous allocation
and is close to the practical limit for further 4diac or OPC UA requests.

### Processor and scheduling limitations

The ESP32 processor is not usually the primary limitation. The repeated failures occurred
when several memory-using clients and tasks ran concurrently. The server loop pins work
to CPU 1 and must regularly call `UA_Server_run_iterate()` and reset the task watchdog.
The 4diac Watch and UaExpert test streams add TCP packet processing, allocation, and
management traffic while Wi-Fi is active.

Task watchdogs and socket closure are therefore downstream symptoms. Increasing the
watchdog timeout alone would hide stalls without freeing heap. Processor throughput
should be considered after memory pressure is stabilized.

### Recommendations for ESP32 DevKit without external memory

Use the server and monitoring modes in separate test phases:

1. Flash and start FORTE.
2. Use 4diac Watch first, with UaExpert disconnected.
3. Add watches one block at a time and remove them after inspection.
4. Stop 4diac Watch before starting or reconnecting UaExpert.
5. Start UaExpert alone and use direct reads before subscriptions.
6. Use at most one subscription and one monitored item.
7. Keep only one OPC UA SecureChannel and Session enabled.
8. Keep the 8 KiB network buffers. Do not lower them to 4 KiB.
9. Restore the OPC UA task stack to 8192 bytes if 6144 gives low
   stack-high-water or stack-overflow symptoms.
10. Remove or avoid optional OPC UA features not used by this application:
    alarms/conditions, event subscriptions, PubSub, encryption/TLS, and generated
    Namespace 0 Full.
11. Keep heap diagnostics while testing, including free heap, largest free block,
    minimum heap, and OPC UA task stack high-water.
12. For simultaneous 4diac Watch and UaExpert on a production-like build, use an ESP32
    board/module with external PSRAM or move one of the servers to a more capable host.

The 4diac IDE `Socket closed` error is a consequence of the ESP32 management connection
ending or not completing its request. It should be interpreted together with the serial
log: heap exhaustion, watchdog reset, stack overflow, socket disconnection, or board reset
must be identified before changing the IDE diagram.
